## 1. Baseline, state space and cost

The original solver constructs a breadth-first search (BFS) table starting at the
solved cube. Each newly reached state receives a move toward a state one layer
closer to solved. Because every allowed move costs one, BFS discovers states in
nondecreasing shortest-path distance. Following the stored reverse moves solves
a query optimally after the table has been constructed.

Fixing one corner removes whole-cube orientation freedom. The remaining seven
corners have 7! permutations. Only six of their twists are independent: the sum
of corner twists is zero modulo 3, so the seventh is determined. The state count
is therefore 7! × 3^6 = 3,674,160. This is a modulo-3 invariant, not an even/odd
parity rule. A permutation rank p and orientation rank o identify a state as
p × 729 + o, with 0 ≤ p < 5040 and 0 ≤ o < 729.

The reachable configurations form the group generated by R, B and D. Its Cayley
graph has a vertex for each configuration and edges for R, R2, R', B, B2, B', D,
D2 and D'. Under the half-turn metric (HTM), each edge costs one, including a
180-degree turn. Enumerating the entire graph with BFS establishes diameter 11
only when both facts hold: a state at distance 11 exists, and no reachable state
has a larger distance. Finding one 11-move solution alone proves neither fact.

The original dominant allocations are:

| Allocation | Bytes |
|---|---:|
| One byte per state for the move toward solved | 3,674,160 |
| Queue of 32-bit state indices | 14,696,640 |
| Factored quarter-turn transition tables | 34,614 |
| Total of these allocations | 18,405,414 |

The queue supports breadth-first enumeration; it is not needed to retain a
single depth-first path. Removing exhaustive target-side enumeration eliminates
both the large queue and the full-state move table. Packing the full distance
table into nibbles would still require 1,837,080 bytes, above 128 KiB.

## 2. Search representation and heuristic

The candidate uses IDA*: depth-first search with an increasing bound on g+h,
where g is the path length and h estimates the remaining distance. The first
bound is h(root). A child is pruned when g+h exceeds the bound; equality remains
eligible. Search frames are stored in a fixed array, avoiding recursion and heap
allocation. Frames retain the parent state, incremental child state, next move,
previous face and selected path move.

Two small pattern databases (PDBs) store exact distances in projected state
spaces: permutation alone and orientation alone. Any complete solution also
solves each projection, so each projected distance is a lower bound on the full
distance. Consequently h(p,o)=max(pd[p],od[o]) is admissible. Adding the two
distances is not justified: one move can improve both projections, so addition
can count the same necessary work twice.

Bounds increase by one up to 11. Before the optimal distance is reached, an
optimal path cannot be removed by the admissible bound test: its prefix length
plus the projected lower bound does not exceed its complete length. The first
successful bound therefore returns a shortest solution, assuming transition
generation, goal checking and traversal are implemented correctly.

Consecutive moves on the same face are omitted. In HTM such a pair either
cancels or combines into one move, so an optimal path never needs it. This
reduces the available moves from nine at the root to six subsequently.

Memory is traded for recomputation: increasing a bound repeats earlier search
work, and the same state may appear through different paths. PDB pruning limits
this work without keeping a full visited-state table on the target.

| Table or search storage | Bytes |
|---|---:|
| Permutation transitions: 3 × 5040 × 2 | 30,240 |
| Orientation transitions: 3 × 729 × 2 | 4,374 |
| Permutation PDB: 5040 bytes | 5,040 |
| Orientation PDB: 729 bytes | 729 |
| These tables combined | 40,383 |
| Explicit search frames: 12 × 32 | 384 |

The measured v4 linked static total is 49,252 bytes, including other constants,
buffers and the reserved stack. It is not merely the table sum. The section
total is a static allocation bound, not a measurement of maximum live stack use.

## 3. C implementation and RV32I constraints

The C reference separates host generation from target search. Host code exports
factored transitions and projected distance tables. The target parses an inline
14-character input, searches, and physically replays the returned path. The host
full-state BFS oracle is used for validation and is not linked into the target.

The candidate avoids expensive target arithmetic through table layout and small
lookup tables. A uint16_t transition index is scaled by two using a shift;
byte-distance tables need no scaling. Row-pointer tables avoid variable row
multiplication. Fixed search frames replace recursive calls and dynamic storage.

The compiler reference is Homebrew riscv64-elf-gcc 16.2.0 with -O2, -march=rv32i
and -mabi=ilp32, plus the recorded freestanding/link options. Its executable name
differs from the assignment's riscv64-unknown-elf-gcc example and is disclosed
rather than silently treated as identical. Instruction audits reject extensions,
undefined symbols and compiler arithmetic helpers.

## 4. Assembly refinement and comparison

Versions v1–v4 combine guided student exercise fragments with AI-provided ABI
and build scaffolding, plus compiled C parsing/replay/runtime. They are historical
mixed-language versions. The current v5 candidate directly implements the entire
target in assembly, including input validation/ranking, physical replay and output.
The v5 runtime and optimizations are AI-authored; provenance is not relabeled as
independent student authorship.

Each frame uses offsets 0/4 for parent p/o, 8/12 for child p/o, 16 for the next
move, 20 for the previous face and 24 for the selected move. The stride is 32
bytes. Transition reads use lhu; PDB reads use lbu; frame fields use lw/sw.
Callers preserve live caller-saved values, non-leaf helpers preserve ra, and the
search entry saves and restores its callee-saved registers.

The renderer-disabled measurements count the entire program, including parsing,
search, replay, output and exit. Code size is linked .text bytes.

Inlining pruning removes argument movement and helper overhead. Inlining the
transition removes three retired call/return instructions per generated child
under the recorded no-relax build. Finally, a0/a1 already hold the child ranks,
so eliminating their two reloads saves two instructions per generated child.
Stores remain because later search steps need the frame contents.

The historical v4 assembly loses to GCC on both displayed inputs and on code size
(20 additional text bytes). Disassembly provides concrete remaining costs:

its own frame-index arithmetic and differing branches. These v4 results
show improvement over v1 but do not beat GCC. That version remains frozen for

## 7. Pipeline observations (historical v4)

The student operated the actual three-move solver ELF on the ordinary RV32I
five-stage processor. Its result was D' B' R', replay PASS, exit 0, with 4,996
cycles and 3,887 retired instructions (CPI approximately 1.29).

For lbu a0,0(t0) at instruction address 0x1264, cycle 667 showed MEM address
0x100007ad and read data 3. At cycle 668 it reached WB, register write enable
was 1, and writeback mux input 0 contained 3. At cycle 669 a0 became 3.
The mux selection control itself was not captured; input data is not evidence
of the select value. Source inspection predicts the MEMREAD selection.

For sw a0,8(s0), s0 was 0x10009ef0. At cycle 750 the destination 0x10009ef8
contained 945. At cycle 753 the store was in MEM and memory write enable was 1;
a0 held 1905. At cycle 754 the memory word became 1905, represented by bytes
71 07 00 00 in little-endian order. The parent permutation at 0x10009ef0
remained 945. The store changes memory rather than either source register.

Register write enable and memory write enable belong to different operations.
They may both be active in one cycle because an older load can be in WB while
a younger store is in MEM. A red stall bubble was also observed while a branch
waited behind loads. This is pipeline control behavior, not a source-level nop.
